# Sparq M7 target architecture, code generation, and VM

## Scope and handout obligations

The semester handout's Phase 7 requires a target ISA, instruction selection and cost, register allocation, assignment of temporaries to registers, DAG-based code generation, and executable or simulated target instructions. Phase 6 also requires machine-dependent optimization. Task 01 establishes the ISA and cost, selects target instructions for every canonical TAC family, and uses a finite-register allocation policy. Task 01 passed an independent audit and was accepted by the student group. Task 02 adds VM execution; its Task 02A audit conditionally passed and Task 02B corrected the confirmed pre-execution validation gap. The student group accepted Task 02 before Task 03. Task 03 implements restricted DAG-based target selection and machine-dependent optimization. The final independent M6/M7 audit passed with no confirmed defects, and the student group accepted M7. The machine-independent optimizer's DAG pass may supply optimized verified IR to this generator; that is distinct from the target DAG pass.

The target is an abstract three-register VM. Its instructions are immutable symbolic records, not encoded bytecode. The VM interprets these records according to this contract and the frozen [language specification](SPARQ_LANGUAGE_SPEC.md).

## Representation and API

`sparq.target` defines `Register` (`R0`, `R1`, `R2`), `SlotKind`, `FrameSlot`, `Op`, `TargetInstruction`, `TargetRoutine`, `TargetProgram`, `instruction_cost`, and `format_target`. `sparq.target_codegen.generate_target(ir_program)` verifies a complete `IRProgram`, lowers its functions in source order and then START, and returns a complete immutable `TargetProgram`. `CodeGenerationError` reports malformed or unsupported input without publishing a partial program. The source IR remains attached as `source_ir` for exact semantic ownership and audit. `python -m sparq.target_codegen examples/hello.spq [--optimize]` compiles and prints the target listing; it does not run it.

Every emitted instruction retains the span of its canonical IR instruction. Synthetic loads, stores and argument pushes use that same span. Each target function and label retains its exact source routine or symbolic identity. Target records validate operand shape, slot registration, call signatures, and branch destinations. The canonical IR verifier supplies path-aware temporary and guard checks; target generation never bypasses it.

## Registers, frames, and calls

Only `R0`, `R1`, and `R2` are physical registers. `R0` is the first source operand, `R1` the second or converted result, and `R2` a binary or comparison result. All three are caller-clobbered. Every source scalar, parameter, array handle, ordinary temporary, BOOL merge temporary, and checked-element guard has one routine-local `FrameSlot`. Frame slots are distinguished by category and ID; exact `VariableSymbol` identity is retained for source storage. The generator uses a deliberate spill-all policy: load an operand immediately before its operation, then store each produced value to its frame slot. Thus no live value relies on a register across a CALL, branch, or other later instruction. This is finite-register allocation, with no implicit extra registers or host temporaries. A later pass may reuse registers only while preserving all effects and trap order.

Each call creates a fresh activation frame with parameter and local slots, saved return position, and its own pending-argument buffer. `PUSH_ARG` copies the value and declared scalar type from a register into that buffer. Immediately adjacent target `LOAD` instructions may appear between argument pushes. `CALL` consumes exactly its function signature's ordered argument tuple, initializes the new frame's parameter slots in declared order, and transfers control to the referenced function. The canonical IR has already evaluated arguments left to right and performed required conversions immediately at each use site; target argument pushes capture those stored results without reevaluation. A recursive call receives a new frame, so caller slots and pending values survive. `RETURN R0` copies the typed result to the caller's `R0`; `RETURN_VOID` returns no result. A discarded non-VOID call may leave a value in `R0`, which the caller ignores. START ends with `HALT`. The VM enforces the frozen configurable call-depth limit, initially 1,000, and raises a controlled stack error on exhaustion.

## Instruction semantics

| Target operation | Operands and required effect |
|---|---|
| `CONST` | Register, typed `Constant`; copy the exact value. |
| `LOAD`, `STORE` | Register and scalar frame slot; copy a value without conversion. Includes ordinary and BOOL merge temporaries. |
| `INIT_SCALAR` | Scalar variable slot, register; initialize at the declaration's executable occurrence. |
| `ALLOC_ARRAY` | Array slot, positive declared length, typed default; allocate a fresh fixed-length instance and default-fill it. |
| `INIT_ELEMENT` | Array slot, statically valid position, register; write one explicit initializer value. |
| `CHECK_BOUNDS` | Guard slot, array slot, index register; check an INT index against the current instance and capture the array instance and index in the guard. Trap if invalid. |
| `LOAD_ELEMENT`, `STORE_ELEMENT`, `READ_ELEMENT` | Use a prior live guard to access exactly the checked instance and index. `READ_ELEMENT` consumes input only after the check. |
| `LABEL`, `JUMP`, `BRANCH_BOOL` | Symbolic destination; `BRANCH_BOOL` requires a BOOL register and selects exactly one destination. Labels have no runtime effect. The loader resolves destinations within the same routine. |
| `UNARY`, `BINARY`, `COMPARE` | Destination register, source register(s), operator token, result or operand type; apply frozen typed arithmetic, logical, and comparison rules. `BINARY` uses left and right registers in order. |
| `TO_FLOAT` | Destination, source register; perform finite binary64 INT conversion and trap on failure. |
| `PUSH_ARG`, `CALL`, `RETURN`, `RETURN_VOID` | Ordered copied argument, symbolic exact function/arity, and result return as described above. |
| `READ_SCALAR`, `SHOW` | Read into a scalar slot or print a register value according to the frozen field parsing and display rules. Side effects occur at this instruction. |
| `HALT` | Terminate START successfully. |

`STORE_ELEMENT` and `READ_ELEMENT` require the still-live checked guard. A subsequent `ALLOC_ARRAY` for that array invalidates earlier guards. The canonical verifier enforces this lifetime before translation. Index evaluation and `CHECK_BOUNDS` precede the RHS work of an indexed assignment; `CHECK_BOUNDS` precedes indexed `READ` input consumption. A guard captures the index value, so later changes to an index variable cannot redirect the access. Explicit initializer positions are already validated statically and use `INIT_ELEMENT` without a dynamic guard.

The VM uses arbitrary-precision signed INT and finite IEEE 754 binary64 FLOAT, preserving subnormals and signed zero. INT division truncates toward zero; signed remainder is `a - trunc(a/b)*b`. Division and remainder by zero, nonfinite FLOAT results, and failed INT-to-FLOAT conversion are controlled runtime errors at their executing instruction. CHAR is one Unicode scalar, STRING is decoded text, and BOOL is exactly TRUE or FALSE. `READ` consumes one whitespace-delimited field under the frozen parsing rules; invalid present input is consumed before the error, exhausted input is an error, and neither changes its target. `SHOW` prints one scalar with a newline, with exact INT decimal, shortest round-trip FLOAT formatting, literal CHAR/STRING text, and uppercase BOOL. No truthiness or implicit conversion is added.

## Task 02 execution API and validation

`sparq.vm.validate_target(target_program)` rechecks immutable target records and routine control flow before execution. In addition to record checks for operand shapes, slot identity, branch labels, parameter and call signatures, it rejects invalid operator/type combinations, misplaced `HALT` or `RETURN`, and any reachable path that falls off a routine. This admits valid manually constructed targets that respect the ISA; it does not require their instructions to duplicate the attached source IR. A malformed target raises `VMRuntimeError` with `INVALID_TARGET` before execution.

The Task 02A audit found that the initial validator checked RETURN and CALL structure but could accept a BOOL register value at an INT return, scalar store, or argument use. Such a malformed target could emit earlier SHOW output before failing during execution. Task 02B adds a path-aware type analysis after structural checks and before the VM runs. It propagates possible types or undefined status for R0–R2, tracks definitely initialized scalar/array slots, associates checked guards with possible array instances, and tracks pending argument types. At a branch join, register and guard possibilities are united while definitely initialized slots are intersected. Loop backedges use a finite worklist fixed point. A use requiring one scalar type is valid only when every reachable incoming path supplies that type. CALL consumes its typed arguments and clobbers all caller registers, defining R0 only for a value-returning function; each function is analyzed with undefined entry registers and initialized parameter slots. Array reallocation invalidates associated guards. Unreachable instructions still undergo structural record checks; register availability and type-flow checks apply only to reachable instructions. Infinite loops are valid target control flow. The validator does not evaluate constants or preempt genuine runtime traps such as division by zero.

`VirtualMachine(target_program, input_stream="...", output_stream=None, max_call_depth=1000, max_array_elements=1_000_000, max_steps=None).run()` executes one program once. `run_target` is a convenience wrapper. `ExecutionResult` reports captured output, consumed READ fields, and executed target instruction count. A text input stream or text string may be supplied; optional output streaming writes each SHOW immediately while retaining captured output. `python -m sparq.vm examples/hello.spq [--optimize]` performs source → semantic analysis → verified TAC → optional verified optimization → target generation → validation → execution. Compilation and runtime failures exit with codes 2 and 3 respectively; success exits 0.

The interpreter uses an explicit stack of frames rather than Python recursion. Each frame has its own program counter, three registers, parameter/local/temporary/merge/guard slots, and ordered pending arguments. `PUSH_ARG` copies a typed value; `CALL` creates fresh storage and moves control to the callee; `RETURN` or `RETURN_VOID` restores the caller and places any result in its `R0`. The default call limit allows 1,000 active function calls; the next call raises `CALL_DEPTH`. `HALT` is valid only in START. Labels resolve to positions within their own routine.

An array allocation creates a new fixed-length instance filled with typed defaults before explicit initializer instructions run. Bounds checks capture both that instance and the evaluated index. Reallocation clears guards for that array; stale guards cannot access the replacement. Allocation has a configurable live-element ceiling (default 1,000,000) and raises `ALLOCATION` before attempting an unreasonable host allocation or evaluating explicit initializers. This is a VM resource safeguard, not a source-language size rule. Released function frames free their accounted array elements. A memory failure during allocation also becomes `ALLOCATION`.

Runtime errors carry a code and source span where one exists: zero division/remainder, nonfinite FLOAT, failed INT-to-FLOAT conversion, bounds, allocation, invalid or exhausted READ, call depth, invalid target or execution state, and I/O failure. Prior SHOW output and consumed READ count remain inspectable on a failed `VirtualMachine`. Integer input and output use bounded decimal chunks internally, preserving exact arbitrarily large values without changing Python's process-wide integer-string safety limit. `max_steps` is an optional explicit execution safeguard for callers and tests; by default infinite source loops continue until externally interrupted.

`tests/test_vm.py` executes source-backed programs through both original and optimized verified TAC with handwritten expected outputs and error categories. It also checks READ consumption, error precedence, recursion, resource bounds, invalid targets, and the CLI. Task 02B added direct-target tests for type mismatches, branch joins, loop backedges, register reassignment, caller-clobbered registers, unreachable type uses, and rejection before I/O. These paired runs provide regression evidence for M6 optimization; they are not a proof of equivalence for every Sparq program. Task 02 was accepted by the student group before Task 03.

Short-circuit decisions are explicit branches in the verified IR and remain branches in target code, so a skipped operand, call, I/O effect, or trap is never emitted on the taken runtime path. The generator does not reorder IR operations. `TO_FLOAT` appears where the IR places its conversion, including before a later binary operand or function argument is evaluated.

## Array allocation and error precedence

Canonical TAC places `InitArray` before any explicit initializer expression and `InitElement` sequence. `ALLOC_ARRAY` therefore attempts allocation and fills all positions with the element default first. If allocation or default fill cannot complete, the VM raises one controlled resource/allocation error at `ALLOC_ARRAY`; no explicit initializer expression has run. If allocation succeeds, explicit expressions are evaluated and converted left to right, with each value stored at its known position. A later initializer error stops execution at that error. This is compatible with the frozen rule requiring left-to-right initializer evaluation and with its stated runtime errors; the frozen specification does not prescribe an opposite ordering for an allocation-resource failure. No frozen text or source syntax is changed. The VM should treat allocation/default fill as one logical success-or-error operation; no partially initialized array is exposed after failure.

## Deterministic instruction cost and optimization boundary

`instruction_cost` is an integer estimate for comparisons, not elapsed time or executed instruction counts. Most instructions cost 1; `LABEL` costs 0; `CHECK_BOUNDS` and `TO_FLOAT` cost 2; `READ_SCALAR`, `READ_ELEMENT`, `SHOW`, and `CALL` cost 5; `ALLOC_ARRAY` costs `3 + length`; `CALL` also adds its argument count; a FLOAT `BINARY` adds 1. The total static listing cost is the sum, including unreachable instructions if present. This is a fixed target model, not a claim that a given VM will have these measured timings.

Task 01 reserved register reuse and DAG selection for later work. Task 03 implements the restricted target pass below; this historical boundary explains why Task 01 alone did not satisfy those handout items.

## Task 03 target DAG and machine-dependent optimization

`sparq.target_optimization.optimize_target(target_program)` returns a new validated `TargetProgram`; `optimize_target_with_report` also returns immutable stage counts, estimated costs, and transformation counts. The input target and attached canonical TAC remain unchanged. Validation runs before every pass and on the final program. A failure raises `TargetOptimizationError` without publishing a partial target. The same three-register ISA, frame slots, calling convention, symbolic labels and VM are retained.

The target DAG pass divides each routine at labels and transfers, then hash-conses typed operator nodes in each reachable pure region. A node records its operator, scalar type, ordered operand dependencies and an available result slot. Slot writes advance local value identities; a cached result becomes unavailable when its slot is overwritten. A repeated node selects a `LOAD` from the available slot instead of another target operation. A subsequent register-liveness pass removes operand loads made dead by that selection. The supported DAG operations are INT `+`, `-`, `*`, non-FLOAT comparisons, INT unary minus and BOOL `NOT`. FLOAT arithmetic/comparisons, division, remainder and conversions are outside this DAG subset. CALL, READ, SHOW, bounds checks, array operations, conversions and other possible effect or trap boundaries clear DAG availability. No DAG value crosses a basic-block join or loop backedge, and operands are never reordered. This is executable target selection, not an illustrative DAG diagram or global CSE.

The register pass tracks a value already in each of R0–R2 within a block and removes only a repeated `LOAD` or `CONST` to the same register when the value is still known. Constant identity includes the exact scalar type and binary64 bits, so `-0.0` and `0.0` cannot be confused by Python's numeric equality. It updates slot versions on writes and READ; CALL clears all register knowledge. A backward register-liveness fixed point over reachable branches and loop edges removes dead `LOAD`/`CONST` definitions. A frame `STORE` into a compiler temporary or BOOL merge slot with no remaining `LOAD` is removed; source variable/parameter initialization and writes remain. The final liveness pass removes definitions exposed by spill cleanup. The ISA has no register-to-register move; these rules reduce redundant slot-to-register transfers and unnecessary spills while the original spill-all mapping remains the safe fallback. No trap, CHECK_BOUNDS, CALL, I/O, ALLOC_ARRAY, or array effect instruction is removed or reordered.

The target listing CLI preserves its default output. `--target-optimize` applies the machine-dependent pass to original TAC; `--optimize --target-optimize` applies it after the machine-independent TAC pass. `--compare-target` prints all three listings and their static instruction counts/costs. The VM CLI accepts the same optimization flags for execution. Programmatic callers can construct the three paths using `generate_target(ir)`, `optimize_target(generate_target(ir))`, and `optimize_target(generate_target(optimize_program(ir, analysis)))`.

For `examples/optimization.spq`, `--compare-target` produced:

| Path | Target instructions | Estimated cost |
|---|---:|---:|
| A: original TAC, ordinary target | 63 | 84 |
| B: original TAC, machine-dependent target | 48 | 69 |
| C: optimized TAC, machine-dependent target | 28 | 46 |

For B, the DAG selected one repeated expression result, register reuse removed nine loads, liveness removed one dead register definition, and spill cleanup removed five temporary writes. The B stages were `63/84` (ordinary), `63/84` (DAG substitution), `54/75` (register reuse), `54/75` (liveness), `49/70` (spill cleanup), and `48/69` (final liveness), where each pair is instruction count/cost. The DAG substitution replaces an operation with an equally priced `LOAD`; its operand loads become removable later. With input `5`, A and B both printed `14`, `12`, `0` on separate lines. These are deterministic model costs, not measured speedups.

A smaller repeated-expression example, `INT a = x + y; INT b = x + y;` after initializing `x=2,y=3`, has the ordinary second `BINARY R2 PLUS R0 R1 INT`. B uses the previously stored `a` value with `LOAD R2 variable3(a):INT`, followed by the existing `STORE` for `b`'s value. Its complete target changes from **33 instructions/cost 41** to **23 instructions/cost 31** after the cleanup passes; both programs print `5` twice.

`tests/test_target_optimization.py` checks all three execution paths using handwritten outputs and error categories, input consumption, calls, recursion, branches, loops, arrays, shadowed symbols, large INTs, source spans, immutability and deterministic listings. It also keeps unused division and bounds checks as negative cases. The final independent audit additionally checked representative original and optimized VM executions and found matching observable results. The coverage is regression evidence, not a proof of equivalence for arbitrary target programs. The Phase 6 machine-dependent category and Phase 7 DAG-based category are implemented and accepted within this documented subset; global DAG scheduling, graph-coloring allocation, FLOAT DAG reuse and cross-block target CSE remain outside scope.
